OpsRelay: AI-assisted incident response

Monitoring that checks whether an app actually works, plus an agent that investigates what broke, proves a fix against the tests, and hands it to a person as a pull request.

The problem

In an outage, noticing that something is wrong is usually the quick part. The slow part is working out what actually failed, whether it’s your code or something you depend on, and getting a safe fix reviewed while people are waiting.

Widely reported Microsoft 365 and Outlook disruptions are a reminder that even mature platforms spend a lot of an incident on diagnosis, verification and communication. We wanted to see how much of that loop an agent could take on without anyone giving up control of what ships.

OpsRelay is a hackathon prototype. It monitors and repairs its own demo applications. It has no connection to Microsoft’s or any other production systems.

What we built

Four parts that run on their own and work together:

  • NovaMart, a shopping storefront Next.js storefront with a FastAPI back end. Pricing is calculated on the server, there’s an inventory oversell guard, and a side-effect-free checkout probe runs the real checkout logic.
  • NovaConnect, a real-time messenger Next.js client with a FastAPI and WebSocket API on SQLite. It has direct and group chats, idempotent sends, delivery and read receipts, and its own functional probe.
  • Uptime monitor and status dashboard A Python worker probes each service for website, availability and core-workflow health, opens and resolves incidents, and writes an evidence hand-off for the agent. The dashboard is built with Next.js.
  • Repair agents A Python orchestrator that picks up failed GitHub Actions runs and live incidents, diagnoses them, tests fixes, and opens draft pull requests. Its state and memory live in MongoDB Atlas.

Both demo apps include controlled failure scenarios, such as a wrong discount calculation, inverted duplicate-message protection, or a dependency that times out. That gives the system real, reproducible bugs to find.

How an incident moves through it

  1. Detect what users would notice

    A homepage that returns 200 doesn’t count as healthy. Each service has a functional probe, such as completing a checkout or sending a message. If it fails, the service is marked degraded even while the site still loads.

  2. Open an incident with evidence

    The monitor records the failure and writes a structured hand-off document for the agent: the failing probes, HTTP status, likely source files, timing, and whether the issue looks like service health or something to investigate.

  3. Reproduce before reasoning

    The agent reruns the failing tests at the failing commit, in a clean copy, before any model call. Flaky or unreproducible failures go to a person instead of a guess.

  4. Diagnose from quoted evidence

    The model gets logs, traceback frames, numbered source and the recent diff. Any evidence it cites has to match those inputs word for word, or the diagnosis is retried and then rejected.

  5. Prove the fix

    It asks for up to three minimal patches and tests each one in a fresh copy. A patch has to pass the failing tests and the full suite, and patches that touch tests, CI, dependencies or secrets are refused.

  6. Hand it to a person

    A passing patch becomes a draft pull request. The intent is saved in MongoDB first, so a crash can’t open duplicates. A person reviews and merges it. The agent never merges.

When the evidence points at a dependency timeout and no recent commit touched that code, the agent recommends an operational step and changes no code. A lot of real incidents look like that, and a code change would be the wrong fix.

Architecture highlights

Crash-safe orchestration

A stage machine with leases stored in MongoDB Atlas. Each incident resumes from its last completed stage after a crash, so the work isn’t lost or done twice.

Repair memory

Past incidents and fixes are stored with embeddings for Atlas Vector Search, so the agent can look up similar failures. A rejected PR switches that memory off.

Idempotent by design

Checkouts carry a stable ID from cart through confirmation, and replays return the stored record. Recovery can then resend just the missing confirmation without creating a duplicate order.

Separate health from recovery

A service can be operational again while its incident stays open, because interrupted checkouts still need reconciling. The dashboard shows both states separately.

What I built

I wrote the first versions of three of the four components. Teammates then integrated and extended them.

  • NovaMart (PR #2) Storefront, product and cart pages, checkout, server-side pricing and promotions, an inventory guard, the checkout health probe, a pytest suite, and the CI workflow template.
  • NovaConnect (PR #9) Real-time messaging over WebSockets with delivery status, read receipts, typing indicators and reactions, a functional monitoring probe, and three controlled failure scenarios with tests.
  • Uptime monitoring and status dashboard (PR #13) The probe worker, the incident lifecycle, uptime calculation, SQLite and MongoDB storage back ends, the agent hand-off document, and the first Next.js dashboard.

The repair-agent pipeline and most of the later dashboard features were built by my teammates. The linked pull requests show exactly what I wrote.

What I’d take into a real team: automated repair is only useful when it’s narrow, verifiable and easy to say no to. Reproduce first, demand evidence, test everything, and leave the merge to a person.
